## 1 引言

### 1.1 编写目的

本文档旨在完整、准确地描述「校园活动综合管理系统」的功能需求与非功能需求，作为系统设计、开发、测试与验收的统一依据。文档以项目当前实际实现为基准撰写，功能条目（FR-xx）与代码行为一一对应，已知限制在附录 C 中如实列出，不混入功能条目。

### 1.2 项目背景

高校校园内各类讲座、比赛、文体活动数量多、分布散，传统依赖海报、群通知的发布方式存在信息触达率低、报名统计靠手工、审核流程不透明等问题。本项目面向重庆师范大学三校区（大学城校区、沙坪坝校区、北碚校区）师生，构建统一的校园活动平台，覆盖「活动发布 → 管理员审核 → 报名（含需审核报名）→ 状态自动流转 → 签到 → 评价 / 评论 → 成果展示 → 通知公告」的完整业务闭环。

系统已按五个任务迭代完成：

1. **任务一：界面现代化改造**——建立红色主题设计体系（`theme.css`，主色 `#A61E2B`，可替换为校 VI 色值）并完成全部 14 个视图的主题变量化改造（琥珀残留与年份残留 grep 自检见附录 B）；
2. **任务二：数据本地化**——种子数据 `data.sql` 全面本地化为重庆师范大学场景（真实学院、三校区、学期语义校准），通过 36 项一致性断言与外键完整性校验（断言清单见附录 B）；
3. **任务三：逻辑检查**——端到端走查全部业务链路并修复 10 处缺陷（修复清单见附录 A）；
4. **任务四：管理员入口**——登录页新增「管理员登录」独立入口，后台路由与权限守卫完备；
5. **任务五：真实用户身份绑定**——注册与资料页绑定学生 10 位学号 / 教师 6 位工号，未绑定身份不得报名活动。

## 2 任务概述

### 2.1 项目目标

构建一个 Web 端校园活动综合管理系统，实现：

- 学生/教师凭真实身份（学号/工号）注册、登录并参与校园活动；
- 任何已登录用户均可创建活动，经管理员审核后公开，报名、签到、评价全流程线上化；
- 管理员通过独立入口进入后台，统一管理用户、活动、分类、评价与公告；
- 活动状态随时间自动流转，无需人工干预；
- 界面采用统一红色主题体系，全站视图使用同一套 CSS 变量（可验证性见 FR-41）。

### 2.2 用户角色

| 角色 | 判定方式 | 主要能力 |
|---|---|---|
| 学生 | `user.role=0` 且 `user_type=0`；已绑定 10 位学号者为完整身份，未绑定者可登录、浏览、评论，但不能报名（受限见 FR-12/FR-10） | 浏览活动、创建活动并担任组织者、报名、签到、评价、评论、收藏、查看成果与通知 |
| 教师 | `user.role=0` 且 `user_type=1`；已绑定 6 位工号者为完整身份，未绑定受限同上 | 同学生权限 |
| 组织者 | 活动报名记录 `role=1` 的用户（含创建者自动登记与管理员指派） | 管理本人活动（编辑、手动开始）、审核需审核报名、发布成果贴、回复评论与评价 |
| 管理员 | `user.role=1` 的账号（种子数据仅 `admin` 一个） | 独立登录入口；活动审核/下架/删除、用户封禁/密码重置、分类管理、评价删除、公告管理；报名活动豁免身份绑定校验 |

### 2.3 运行环境

| 层 | 技术 | 版本/说明 |
|---|---|---|
| 后端 | Java + Spring Boot | Java 17（`pom.xml` `java.version=17`），Spring Boot 3.2.0（`spring-boot-starter-parent` 3.2.0） |
| 持久层 | MyBatis Plus + SQLite | `mybatis-plus-spring-boot3-starter`、`sqlite-jdbc`；数据库文件由 `DatabaseInitializer` 启动时自动初始化 |
| 安全 | Spring Security + JWT + BCrypt | 无状态会话（`SessionCreationPolicy.STATELESS`），BCryptPasswordEncoder 存储口令 |
| API 文档 | SpringDoc OpenAPI | Swagger UI：`http://localhost:8080/api/swagger-ui.html` |
| 前端 | Vue 3.5 + TypeScript + Vite 7 + Element Plus + Pinia | 端口 5173，`/api` 代理到后端 8080 |

| 硬件/OS | 开发用普通 PC 即可 | 2 核 CPU / 4GB 内存以上；Windows 10/11、macOS、Linux 均可（SQLite 为嵌入式存储，无独立数据库进程） |

### 2.4 假设与约束

- **A-1 数据库容量**：SQLite 单机嵌入式，面向课设演示规模（百级用户、百级活动）设计，不做分库分表与集群部署规划。
- **A-2 单管理员**：种子数据仅一个管理员账号（`admin`），管理员创建的活动同样进入待审核队列（见 FR-15 说明）。
- **A-3 时间基准**：种子活动日期以**应用启动时刻**为基准按相对天数（`datetime('now','+N days')`）动态生成；`data.sql` 注释标注的学期语义（2026 年 11 月 / 2026-2027 学年第一学期期中）对应当前开发窗口（详见 FR-42 与 NFR-13 的统一说明）。
- **A-4 身份校验为模拟规则**：学号/工号仅做格式与唯一性校验，不对接真实学籍/教工系统；生产对接点集中于 `UserServiceImpl.validateIdentity`。
- **A-5 风险声明**：课设阶段不设独立测试环境与生产环境；演示账密（`admin/test`）直接用于演示（发布前检查项见 AC-24）。

## 3 功能需求

活动状态机编码（`Activity.java:58` 注释与实现一致）：

> **-2 已下架、-1 已拒绝、0 草稿、1 待审核、2 报名中、3 即将开始、4 进行中、5 已结束**

### 3.1 认证与身份绑定模块

- **FR-01 用户注册**：`POST /auth/register`。必填项：用户名、密码、身份类型（user_type）及对应学号/工号；用户名全局唯一（重复抛 `BusinessException(400, "用户名已存在")`）；密码经 BCrypt 加密存储（系统不设密码强度规则，属已知限制 L-8）；注册成功默认 `user.role=0`（普通用户）、`status=1`（正常）。（`UserServiceImpl.register`）
- **FR-02 注册身份选择**：注册页必须选择「学生 / 教师」身份；学生填写学号、教师填写工号，身份切换时清空另一身份的输入，前端仅提交所选身份的编号。
- **FR-03 学号校验**：学生学号必须匹配 `^202[0-6]\d{6}$`——10 位数字且前 4 位为入学年份 2020~2026；不合法返回中文错误提示。（`UserServiceImpl.java:35`，前后端正则一致）
- **FR-04 工号校验**：教师工号必须为 6 位数字。
- **FR-05 唯一性校验**：学号/工号在未删除用户（`deleted=0`）中全局唯一，重复时返回中文错误。
- **FR-06 登录**：`POST /auth/login` 经 `AuthenticationManager` + BCrypt 比对口令，成功后签发 JWT，有效期 **24 小时**（`application.yml` `expiration: 86400000`）；系统无 Token 刷新/续期机制，过期后走 FR-09 重新登录。
- **FR-07 管理员登录入口**：登录页提供「普通登录 / 管理员登录」双 Tab（`Login.vue:94-98`）；管理员 Tab 复用同一登录接口，成功后校验 `role===1`，非管理员提示「该账号不是管理员，无法登录管理后台」且**不写入 token/userInfo**；管理员登录成功跳转 `/admin/activities`。
- **FR-08 封禁账号不可登录**：`status=0` 的账号登录抛 `DisabledException`，返回 401「该账号已被禁用」；已持有的存量 JWT 在后续请求中同样失效走 401 登出链路。封禁仅影响登录与 API 访问，名下已发布内容（活动、评论、成果）不做自动下架/删除，由管理员按需手动处理（已知限制 L-6）。
- **FR-09 Token 失效自动登出**：后端对未认证请求返回 HTTP 401 + 统一 JSON `{code:401, message, data:null}`（`SecurityConfig.authenticationEntryPoint`）；前端拦截 401 后清除本地凭证并跳转登录页。
- **FR-10 历史用户补绑**：已注册但未绑定身份的用户可通过 `POST /user/bind-identity` 补填学号/工号，校验规则与注册一致（FR-03~FR-05）；已绑定者拒绝重复绑定。（`UserController:169`）
- **FR-11 老库迁移**：启动时 `DatabaseInitializer.migrateUserIdentityColumns()` 用 `PRAGMA table_info(user)` 检查 `user_type`/`teacher_id` 列，缺失则 `ALTER TABLE` 补列并建索引，老库升级不丢数据。
- **FR-12 未绑定身份禁止报名**：未绑定学号/工号的用户调用报名接口返回「请先完善身份认证（绑定学号/工号）后再报名活动」；管理员（账号角色=1）豁免。（`ActivityParticipantController:102-106`）
- **FR-13 主动退出登录**：导航栏用户下拉菜单提供「退出登录」（`NavBar.vue:87`）；点击后清除本地 token/userInfo（`stores/user.ts:32-37,106-109`）并跳转回首页（`NavBar.vue:43-46` `router.push('/')`）。Token 仍有效期内再次访问受保护页面时由路由守卫（FR-39）拦截至登录页。
- **FR-14 密码管理**：普通用户**无**修改密码、找回密码功能（`UserController` 仅提供 `/info`、`/upload-avatar`、`/update-info`、`/bind-identity` 四个端点），属范围外功能（后续迭代项）；管理员可对指定用户重置密码（`AdminUserController:193` `resetPassword`）。

### 3.2 活动全生命周期模块

- **FR-15 活动创建**：**任何已登录用户**（学生、教师、管理员）均可创建活动，后端仅校验登录状态（`ActivityManageController.create:92-135` 不限角色）；创建即置 `status=1 待审核`，初始化统计字段（浏览/收藏/评论/参与人数均置 0）；组织者经 `setUserAsOrganizer` 自动登记（FR-16）。（「草稿 0」为预留状态，`CreateEvent` 不提供暂存草稿路径。）创建接口不做时间合法性校验（如 `end > start`、报名截止早于开始时间等），约束见附录 C 已知限制 L-3。管理员创建的活动同样进入待审核队列，在种子仅单管理员场景下（假设 A-2）由同一账号审核。
- **FR-16 组织者自动登记**：创建者自动写入一条报名角色=1（组织者）的报名记录，**初始状态=1（已通过）**（`ActivityPermissionServiceImpl.setUserAsOrganizer:96-113`），计入 `organized_count` 与分类活动数。
- **FR-17 活动审核**：管理员通过 `/admin/activities/approve/{id}` 审核活动：通过置 `status=2 报名中` 并向组织者发送审核结果通知；`/admin/activities/reject/{id}` 拒绝置 `-1`；`/admin/activities/take-down/{id}` 下架置 `-2`；`/admin/activities/delete/{id}` 逻辑删除。**异常流**：被拒绝（-1）或下架（-2）为终态——组织者仍可在「我的活动」编辑活动内容字段（FR-25 不改状态），但系统无「重新提交审核」接口，须联系管理员重新处理；下架后已产生的报名记录保留，签到/评价等操作因活动状态不满足前置条件而自然不可进行。
- **FR-18 状态自动流转**：调度器每 30 秒（`@Scheduled(fixedRate=30000)`）扫描：活动开始前 30 分钟 `2→3 即将开始`；到达开始时间 `2/3→4 进行中`；到达结束时间 `2/3/4→5 已结束`。（`ActivityStatusScheduler.java:31`）**边界**：状态 1（待审核）与 0（草稿）不参与自动流转——待审核活动错过开始时间不会被自动开始或结束，须管理员先审核；「审核通过时开始/结束时间已过」的活动在通过置 2 后由下一调度周期直接流转至 5（已结束），系统不拦截该情况。
- **FR-19 手动开始**：组织者或管理员可手动开始活动，`POST /activities/status/start/{id}`。**权限两条判据**：① 报名角色=1（组织者本人，`permissionService.isOrganizer`）；② 账号角色=1（管理员可开始他人活动）。（`ActivityStatusServiceImpl.startActivity:67-81`）**前置状态**：仅 `status=2` 或 `3` 可手动开始，其余状态返回 400「活动状态不允许开始」（`ActivityStatusController:122-135`）；允许提前于预定开始时间开始，开始时系统将 `start_time` 重置为操作时刻（`ActivityStatusServiceImpl:92`），以避免与自动流转（到达开始时间判定）互斥冲突；手动开始后向相关用户发送状态变更通知。
- **FR-20 活动报名**：`POST /activities/{id}/join`。前置校验按序执行（`ActivityParticipantController:102-148`）：① 身份绑定校验（FR-12）；② 重复报名拦截（存在未删除报名记录即拒绝，取消后可重新报名，见 FR-23）；③ 仅 `status=2` 的活动可报名；④ 报名时段校验（`registration_start_time`/`registration_end_time` 为 null 时视为不限制）；⑤ 名额校验：`max_participants > 0` 且 `current_participants ≥ max_participants` 时拦截「报名名额已满」（0 或 null 表示不限额）。报名附件：最多 **3 张**图片，单张 ≤ **10MB**，仅接受 `image/*` 类型，任一超限直接拒绝报名（不压缩、不截断）（`ActivityParticipantController:150-176`）；报名备注 remark 无长度限制（schema 为 `TEXT`，已知限制 L-7）。
- **FR-21 需审核报名**：`need_review=true` 的活动，报名置报名状态 `0 待审核`、**不占用名额**，返回「报名成功，等待审核」；组织者通过 `POST /activities/manage/registrations/{id}/review` 审核，仅允许「1-通过 / 2-拒绝」，其他值返回错误（`ActivityManageController:467-470`）；仅待审核（0）状态的记录可被审核（`ActivityRegistrationServiceImpl:90`）。**通过时**：置报名状态 1、计入 `current_participants` 与用户 `participated_count`、向报名者发送审核结果通知（`ActivityRegistrationServiceImpl:103-124`）。**已知边界（L-4）**：通过时不复核名额上限，待审核池大于剩余名额时全部通过将导致人数超限；并发抢报名场景接口为顺序校验无锁，SQLite 单写者特性缓解但不杜绝极端并发下的超额。
- **FR-22 直接通过报名**：`need_review=false` 的活动，报名即置报名状态 `1`，立即计入人数与 `participated_count`。
- **FR-23 取消报名**：`DELETE /activities/{id}/cancel-join`。**记录形态**：取消为**逻辑删除**报名记录（`ActivityParticipantController:251` `removeById`），状态枚举中无「已取消」值；取消后可重新报名（重复报名拦截仅针对未删除记录）。**前置条件**：仅活动 `status=2`（报名中）可取消（活动开始后不可取消）；已签到（报名状态 3）的记录不可取消（「您已签到，无法取消报名」）。**回退规则**：仅报名状态 1（已通过）的记录回退 `current_participants` 与 `participated_count`（待审核 0 从未计数，无需回退）（`ActivityParticipantController:254-268`）。已取消（逻辑删除）的待审核记录不再出现在组织者审核列表中。
- **FR-24 活动签到**：`canCheckIn` 判定两条硬条件：报名状态=1（已通过）**且** 活动 `status=4`（进行中）（`ActivityPermissionServiceImpl.canCheckIn:57-70`）；状态 3（即将开始）不可签到。操作形式：活动详情页「签到」按钮，由本人登录后调用，系统无扫码签到、无代签、无补签机制（`CheckInRecordServiceImpl.checkIn` `check_in_type=2 手动签到`）。签到幂等（重复签到返回失败，`CheckInRecordServiceImpl:33-36`）；签到成功将报名状态置 `3 已签到`（`:64-66`）。**边界（L-5）**：后端 `canCheckIn` 仅校验报名状态，未排除报名角色=1 的组织者记录——组织者本人技术上也满足签到条件；前端签到按钮对组织者/管理者隐藏（`EventDetail.vue:523-529`）。**闭环缺口（L-5）**：仅进行中可签 + 评价要求已签到 ⇒ 活动进行中漏签者将永久失去该活动的评价资格，系统无补签通道。
- **FR-25 活动修改保护**：组织者更新活动（`PUT /activities/manage/update/{id}`）前置权限：报名角色=1 且该报名状态=1（`canModifyActivity`）。请求体中以下 **10 个受保护字段**强制置 null（MyBatis Plus 不更新 null 字段），集合封闭（`ActivityManageController:180-190`）：`organizer_id`、`status`、`current_participants`、`view_count`、`favorite_count`、`comment_count`、`avg_rating`、`review_count`、`create_time`、`deleted`。**已知边界（L-2）**：已通过审核的活动，组织者编辑标题/时间/名额等内容字段**不触发重新审核**，状态保持不变。
- **FR-26 活动收藏**：登录用户可收藏/取消收藏活动，活动 `favorite_count` 同步维护。

### 3.3 评价、评论、成果与通知模块

- **FR-27 活动评价**：`POST /reviews/create`。**参与者判定完整条件**（`isParticipant`，`ActivityPermissionServiceImpl:40-49`）：报名**角色=2（参与者）且报名状态 ∈ {1 已通过, 3 已签到}**——组织者记录（角色=1）即使状态=1 也被排除。评价前置：活动 `status=5`（已结束）+ 通过参与者判定 + 已签到（`ActivityReviewController:31`）+ 评分 1~5 + 每人对同一活动仅一次（防重复）。评价不可修改（无更新接口，仅可删除）；无评价时间窗限制（活动结束后任意时间可评价）。**漏签缺口见 FR-24 已知限制 L-5。**
- **FR-28 评价回复与删除**：**组织者回复**：活动组织者可回复本人活动的评价（`GET /reviews/organizer` 查看本人组织活动收到的评价，`POST` 回复接口回复可覆盖更新，对应前端页面 `/organizer/reviews`，`ActivityReviewController:130-160`）。**删除**：`DELETE /reviews/delete/{id}` 仅管理员可删除——校验分两层：控制器层账号角色判定（非管理员返回 403「仅管理员可删除评价」，`ActivityReviewController:205-208`）+ 服务层记录存在性校验（不存在返回 404，`ActivityReviewServiceImpl:216-221`）；删除后自动重算该活动 `avg_rating` 与 `review_count`（`:223-227`）。对应后台页面 `/admin/reviews`。
- **FR-29 评论发表与回复**：活动详情公开查询评论（无需登录）与评论数；登录用户发表评论；支持 `POST /comment/reply/{parentId}` 楼中楼回复，回复时向被回复者发送通知（`CommentController:202`）。
- **FR-30 评论删除**：作者本人、活动组织者、管理员可删除评论，评论计数同步维护。
- **FR-31 成果展示**：组织者或管理员可发布/编辑/删除活动成果贴，每个活动限一贴（`GET /results/exists/{activityId}` 预检）；发布时向已通过报名的参与者发送通知（`ActivityResultController:362`）；成果贴支持图片上传（`/results/upload-images/{activityId}`）。对应前端页面：成果列表 `/achievements`、详情 `/achievement/:id`、编辑 `/edit-achievement`；发布入口位于活动详情页组织者管理面板（B-3 双向对应）。
- **FR-32 通知中心**：用户侧接口：通知列表、未读数、单条已读、全部已读、删除（`NotificationController:61-168`）。**系统自动通知为封闭清单**，共 9 类事件：

| # | 事件 | 触发时机 | 接收人 | 代码位置 |
|---|---|---|---|---|
| 1 | 活动审核结果（通过/拒绝） | 管理员执行 approve/reject | 组织者 | `AdminActivityController:197/231` |
| 2 | 报名审核结果 | 组织者通过待审核报名 | 报名用户 | `ActivityRegistrationServiceImpl:124` |
| 3 | 活动状态变更 | 状态流转至 4（进行中） | 已通过/已签到的报名用户 | `ActivityStatusServiceImpl:215` |
| 4 | 活动开始提醒 | 进入进行中 | 组织者与参与者（区分文案） | `ActivityStatusServiceImpl:226/233` |
| 5 | 活动已开始提醒 | 进行中且未发送过（防重） | 组织者/参与者 | `ActivityStatusServiceImpl:249`（`hasActivityReminderSent` 防重） |
| 6 | 3 天/1 天日历提醒 | 调度器每日扫描即将开始的活动 | 组织者/参与者 | `ActivityStartReminderService.sendCalendarDayReminders`（调度器内） |
| 7 | 评论回复 | 他人回复本人评论 | 被回复者 | `CommentController:202` |
| 8 | 成果发布 | 组织者/管理员发布成果贴 | 已通过报名的参与者 | `ActivityResultController:362` |
| 9 | 系统公告 | 管理员发布公告（FR-33） | 按 publishScope 广播 | `NotificationServiceImpl.createAnnouncement` |

  除公告为广播记录外，其余事件均为定向个人通知（写入接收人 `user_id`）。
- **FR-33 公告管理**：**后端 API 挂载于 `/admin/notifications`**（`AdminNotificationController:50` `@RequestMapping`），由 FR-34 双重防护覆盖；**前端页面路由**为 `/notifications/send-announcement` 与 `/notifications/manage-announcements`（不在 `/admin` 前端路径下，由前端守卫 `requiresAdmin` 控制）——两层路径不同但各自有权限控制。公告字段：标题、内容、发布范围 `publishScope`（ALL/USER/ADMIN）、是否置顶 `isPinned`、发布时间 `publishTime`（为空立即发布）、状态 `status`（0 草稿/1 已发布）、公告分类 `announceCategory`（SYSTEM/ACTIVITY/URGENT）；支持编辑与撤回（recall）。**分发机制**：公告为**广播式**——每条公告仅插入一条 `user_id=0` 的公共记录（`NotificationServiceImpl:52-69`），不逐用户复制；用户查询通知列表时由 SQL 合并满足 publishScope 的广播记录（`selectUserNotificationPage`）；用户标记已读时直接更新公共记录的 `is_read`（`markAsRead` 匹配 `user_id=本人 OR user_id=0`，`NotificationServiceImpl:415-425`）。

### 3.4 管理员后台模块

- **FR-34 后台路由防护**：SecurityConfig 对 `/admin/**` 强制 `hasRole("ADMIN")`（`SecurityConfig.java:65`），四个 Admin 控制器（用户 `/admin/users`、活动 `/admin/activities`、分类、公告 `/admin/notifications`）类级再加 `@PreAuthorize("hasRole('ADMIN')")`——**后端 API 双重防护成立**（四个控制器均挂 `/admin/**` 前缀）；普通用户越权访问返回结构化 403 JSON。
- **FR-35 用户管理**：管理员分页查询用户；关键词搜索匹配 **5 个字段**（用户名、昵称、学号、工号、邮箱，`AdminUserController:57-74`，不含姓名与手机号）；按身份筛选（学生 0/教师 1/未绑定 -1）；封禁/解封（置 `status=0/1`）；重置密码（FR-14）。封禁联动范围见 FR-08（已知限制 L-6）。
- **FR-36 活动管理**：管理员操作清单（`AdminActivityController:77-367`，全部封闭）：① 待审核列表 `/pending`；② 全量列表 `/list`；③ 详情 `/detail/{id}`；④ 通过 `/approve/{id}`；⑤ 拒绝 `/reject/{id}`；⑥ 删除 `/delete/{id}`（逻辑删除）；⑦ 下架 `/take-down/{id}`；⑧ 刷新状态 `/refresh-status`（触发一次即时状态重算）。管理员**无**直接置 4/5 的接口、无恢复下架活动的接口（重新上架须借助 FR-25 组织者编辑不生效的说明之外的管理员侧手段，当前未提供，见已知限制 L-2）。
- **FR-37 分类管理**：管理员维护活动分类的增删改查，分类 `activity_count` 与活动分布保持一致（种子数据由断言校验，附录 B）。
- **FR-38 评价管理**：管理员在 `/admin/reviews` 集中查看全站评价并可删除违规评价（与 FR-28 删除链路一致）。
- **FR-39 前端权限守卫**：全局路由守卫三段判定（`router/index.ts`）——未登录访问 `requiresAuth` 页跳 `/login`；已登录访问 `guestOnly` 页跳 `/events`；非管理员访问 `requiresAdmin` 页跳 `/events`；`/admin` 重定向至 `/admin/activities`。守卫读取 localStorage 判定登录与管理员身份，仅作展示层引导，安全边界在后端（FR-34）。

### 3.5 数据展示与主题模块

- **FR-40 活动列表与搜索**：活动列表支持分类筛选（categoryId）、状态筛选（2/3/4/5）、关键词搜索与分页；**关键词仅匹配活动标题**（`Activity::getTitle` like，`ActivityController:58,71-72`），不匹配描述与标签。加载中显示骨架屏，无数据显示 `el-empty`（含四个表格型管理页经 `#empty` 插槽补充空状态）。

## 4 非功能需求

### 4.1 性能需求

- **NFR-01 列表响应**：常规列表接口（活动、评论、通知）分页返回（默认每页 10 条，可调）。**课设阶段不做量化性能指标承诺**（不设 P95/并发量目标）；用户可感知的加载态由骨架屏保证（FR-40）。若后续需要量化指标，应在独立性能需求文档中补充。
- **NFR-02 状态流转实时性**：活动状态由调度器每 30 秒全量刷新一次，状态延迟不超过 30 秒；管理员可经 `/admin/activities/refresh-status` 手动触发即时重算。
- **NFR-03 资源加载**：主题变量集中在单一 `theme.css`（约 186 行）内，修改主题色不需要重新构建组件。

### 4.2 安全需求

- **NFR-04 口令安全**：所有口令经 BCrypt 散列存储，种子数据口令 `test` 由启动时 `encryptInitialPasswords()` 自动加密，库中不落明文。登录页底部演示账密提示（FR-07/AC-16）仅限课设演示使用，真实发布前必须移除并修改默认口令（发布检查项 AC-24）。
- **NFR-05 认证机制**：JWT 无状态认证（`STATELESS` 会话），有效期 24 小时（FR-06），JWT 过滤器在 `UsernamePasswordAuthenticationFilter` 之前挂载；无刷新机制。
- **NFR-06 后端权限校验**：权限判定以后端为准——`/admin/**` 路由级 + 控制器类级双重校验（四个 Admin 控制器均覆盖，FR-34）；前端守卫仅作展示层引导，不作为安全边界。
- **NFR-07 统一错误响应**：所有接口返回统一 `Result{code, message, data}` 结构。**code 取值封闭清单**：`200` 成功；`400` 参数/业务校验失败（含 `BindException` 字段错误聚合）；`401` 未认证/凭证失效/账号禁用/用户名密码错误（`GlobalExceptionHandler:36-88`）；`403` 权限不足/越权访问；`404` 资源不存在（BusinessException 携带）；`500` 系统异常兜底（`Result.error(String)` 默认码，GlobalExceptionHandler 兜底「系统繁忙」）。
- **NFR-08 越权防护**：活动更新 10 个受保护字段强制置空（FR-25）、报名审核仅接受 1/2 状态值（FR-21）、评价删除仅管理员（FR-28）、`/user/update-info` 不可修改用户名/密码/角色/状态，均由后端强制。
- **NFR-09 身份真实性**：学号/工号格式 + 全局唯一校验（FR-03~FR-05），为模拟校验规则（假设 A-4），生产可替换为学籍/教工接口对接（对接点集中在 `UserServiceImpl.validateIdentity`）。

### 4.3 可用性需求

- **NFR-10 界面一致性**：全部视图使用 `theme.css` 语义变量，无硬编码琥珀色值。**可复现验收口径**：扫描范围 `eventsys_front/src/`（含 `.vue`/`.css`），匹配 1.3 节定义的琥珀色十六进制值清单（`#f59e0b`/`#d97706`/`#fef3c7`/`#fffbeb`/`#fde68a`）及琥珀 rgba 阴影；任务一会话内自检残留计数为 0（自检命令与结果记录于附录 B）。
- **NFR-11 空状态与反馈**：列表页骨架屏 + `el-empty` 空状态；操作结果通过 toast 反馈，报名被拒/待审核均有明确文案。
- **NFR-12 中文语境**：全部界面文案、错误提示为中文；浏览器语言标记 `zh-CN`。
- **NFR-13 数据可维护性**：种子数据以**应用启动时刻**为基准按相对偏移（`datetime('now','+N days')`) 动态生成，活动日期不因部署日期推移而落在过去；但活动**主题与学期语义**（如「期中季」「秋季运动会」）与基准学期绑定（假设 A-3），更换部署学期时须按 FR-42 校对。

**备份与恢复**：SQLite 为单文件库，备份即拷贝数据库文件；系统无内置备份任务（课设范围外，人工拷贝）。**容量估算**：按假设 A-1 演示规模（百级用户/活动、千级报名/通知），库体积在数十 MB 以内，无需分表。
